# Технологии и ML-модели BuildWatch

В BuildWatch есть два разных контура машинного обучения: компьютерное зрение
для анализа изображений стройплощадки и языковая модель для текстового помощника.
Детекция выполняется локально; помощник обращается к внешнему API.

## 1. Детектор строительной техники

### Модель и назначение

В рабочей конфигурации детектор `equipment` загружает локальный файл
`weights/equipment_v12ft_2_best.pt`. Скрипт инференса реализован через
**Ultralytics YOLO и PyTorch** и задаёт закрытый детектор семейства
**YOLOv8m** с размером входа **1280 × 1280**. Он возвращает для каждого
объекта класс, уверенность и прямоугольную рамку `[x1, y1, x2, y2]`.
Слово «закрытый» означает, что модель выбирает из заранее обученных классов,
а не ищет произвольные объекты по текстовому запросу.

Целевой набор включает восемь видов техники: экскаватор, самосвал, каток,
кран-манипулятор, бетоносмеситель, бульдозер, грузовик и автокран. Метки
приводятся к каноническим названиям BuildWatch перед применением правил.

### Обучение и данные

Разметки разных источников приводятся к единой онтологии и формату YOLO:
изображение сопровождается файлом с классами и координатами рамок. В известном
снимке набора v11 было 68 910 обучающих и 4 369 отложенных изображений.
Использовались внешние наборы строительной техники, снимки площадок,
проверенные и очищенные метки, удаление дублей и отдельные примеры с мелкими
объектами. Отложенная выборка отделена от обучения.

Этот процесс включает дообучение YOLO на целевых классах. Вспомогательные
инструменты для подготовки данных используют визуально-языковые модели для
предварительной разметки или проверки спорных объектов; такие подсказки
проверяются и не считаются автоматически эталонной разметкой. Скрипты
`sonnet_annotate.py` и `sonnet_review.py` по умолчанию обращаются к
`claude-sonnet-4-6`; `vlm_label_dataset.py` задаёт Grounding DINO Tiny для
предложений рамок и Qwen2.5-VL-3B-Instruct для их текстовой проверки.
Это офлайн-инструменты подготовки, а не часть обработки пользовательского
снимка.

### Инференс в приложении

API ставит задачу в SQLite, фоновый worker передаёт снимок локальному
детектору, а тот запускается с **CPU runtime** и размером изображения 1280.
Инференс объединяет полный кадр и **SAHI** (нарезка окна) для мелкой техники,
затем склеивает боксы в координатах исходного кадра. Порог confidence при
выводе боксов — 0,15; отдельные правила BuildWatch используют более строгие
пороги для отображения предупреждений и ручной проверки. Результат
проверяется по схеме и диапазонам координат до записи в базу. Ошибка
обработки получает статус `failed` и не интерпретируется как
«техника отсутствует».

Путь `equipment-v2` оставлен как отдельный сравнительный вариант; старые
названия `yolo-world`, `uisikdag`, `thalos` и `ensemble` нормализуются к
текущему `equipment`. Эти имена совместимости не означают, что перечисленные
модели сейчас работают в ансамбле.

### Что говорят метрики

Для раннего `equipment_v2` на внешнем holdout зафиксировано mAP@50 = 0,786.
Это результат конкретной более ранней версии и внешней выборки. Он не
переносится на настроенный сейчас checkpoint `equipment_v12ft_2_best.pt` и
не доказывает качество на московских камерах. В репозитории нет отчёта
независимой оценки текущего v12 checkpoint на замороженной московской
разметке; поэтому здесь для него не приводится заявленная точность.

## 2. Языковая модель помощника

Помощник BuildWatch использует **OpenCode Zen Chat Completions API**. Если
переменная `BUILDWATCH_ZEN_MODEL` не задана, запрашивается модель
`glm-5.3-flash`. Параметр `reasoning_effort` берётся из
`BUILDWATCH_ZEN_REASONING_EFFORT` и ограничен значениями
`low|medium|high|xhigh|max|none|adaptive` (по умолчанию `low`). Сервис
передаёт модели вопрос и ограниченный контекст из
BuildWatch: данные объекта, этапы плана, снимки, детекции и предупреждения.
Ответ запрашивается в структурированном JSON с ответом, ссылками на
доказательства и, при явном запросе, предложением сдвинуть даты этапа.

Модель не анализирует изображение и не принимает решение о наличии техники:
это делает локальный YOLO-детектор. Помощник формулирует ответы по уже
сохранённым данным. Перенос дат не применяется автоматически: приложение
создаёт предложение, которое пользователь подтверждает отдельно. API-ключ
хранится и используется на сервере, а не в браузере.
